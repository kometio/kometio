# 0045 — A setup token gates the first-run wizard

**Status**: Accepted — 2026-09-05

## Context

The first-run wizard ([ADR-0044](0044-runtime-site-resolution-in-the-editor.md)
and the PR before it) is unauthenticated by necessity — it runs when there
is nobody to authenticate as. What gated it was a single condition: **the
deployment has no tenant yet**.

That is not a gate against a person, only against a second run. Between
`docker compose up` and the owner filling in the form, anyone who reaches
`admin.<domain>` becomes the administrator of somebody else's
installation — with their own email and password. The real owner then
finds "already set up" and has no way in at all. `GET /setup/status` makes
it worse by design: it announces to anyone who asks that an installation is
still unclaimed.

The window is not theoretical. DNS often resolves before the owner opens a
browser, and freshly exposed hosts are scanned continuously.

**This is WordPress's `wp-admin/install.php` race**, and WordPress has not
solved it either: once `wp-config.php` exists — which is always true on a
Docker or managed deployment, where DB credentials come from the
environment — `install.php` will hand the site to whoever loads it first.
Ghost, Nextcloud's Docker image, Umami and Plausible are all in the same
position. The advice is "complete the installation immediately", which is a
hope, not a control.

Software that does close it uses one of three patterns:

|                   | How                                                        |                                        |
| ----------------- | ---------------------------------------------------------- | -------------------------------------- |
| GitLab            | initial root password written to a file only root can read | secret where only the operator reaches |
| Jupyter           | token printed to the log, carried in the URL               | same                                   |
| Vaultwarden       | admin panel behind `ADMIN_TOKEN` in the environment        | secret the operator chooses            |
| Discourse, Sentry | first admin created only from a CLI                        | no network surface                     |

## Decision

**`POST /setup` requires a setup token, generated by the API and printed to
its log at boot.** Whoever can read the server's log is the operator; that
is the bar, and it is a stronger one than any captcha.

Chosen over an operator-supplied `SETUP_TOKEN` in `.env` for two reasons
that are concrete rather than stylistic:

- **Entropy is guaranteed.** A generated token is always 256 bits from
  `randomBytes`. A human-chosen one is whatever the operator typed while in
  a hurry, and `POST /setup` is reachable by anyone.
- **The gate cannot be switched off by a configuration mistake.** The
  server always generates one; there is no value of any variable that
  leaves setup ungated. An `.env`-supplied secret is one forgotten line
  away from being empty — and this repository has just spent a night on a
  required variable whose own documentation said to leave it unset.

The honest cost, accepted: the token passes through application logs, which
some deployments ship elsewhere. It is bounded — the token is worthless the
moment setup completes, and it is cleared from memory then.

**Held in memory, regenerated on every boot.** The alternatives are worse
in opposite directions: persisting it in plaintext would put a live
credential at rest, against the convention every other token here follows
(`sessions` and `verification_tokens` store SHA-256, see
`@kometio/opaque-token`); persisting only its hash would mean it could never
be printed again, so an operator who missed one log line would be stuck
with no way to produce a new one. Regenerating per boot is always
printable, never at rest, and invalidates its predecessor. The cost — a
restart invalidates a token someone already copied — is stated in the log
line itself and in the rejection message.

**The write is now rate-limited** (`ThrottlerGuard`, the same 5/minute as
login). Its previous comment argued rate limiting was pointless because
only one request could ever succeed; that stopped being true the moment
there was a secret to guess.

On `POST` alone, though, not on the controller. A class-level guard puts
`GET /setup/status` — which the editor polls on every route load — into the
same bucket, so a couple of page refreshes lock the owner out of their own
form. That was measured on a real container before it was written down.

**The token is checked before anything else** — before the password is
hashed. Argon2 is deliberately slow, and hashing first would turn an
open endpoint into a way to spend the server's CPU on demand.

## Consequences

- One extra documented step for the self-hoster: read the log
  (`docs/self-hosting.md`, step 5). This is the whole cost.
- A restart between reading the token and submitting the form invalidates
  it. The rejection message says so and says where to look again.
- `GET /setup/status` still reveals that an installation is unclaimed. That
  is now much less useful to an attacker — knowing a door is unlocked does
  not help when it needs a key — and the editor needs it to decide between
  the wizard and the login screen.
- This protects _who may create_ the administrator. It does not verify that
  the email typed into the wizard belongs to that person; a code emailed to
  it at first login is the complement, and is in the backlog.
