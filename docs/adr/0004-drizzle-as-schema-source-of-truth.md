# 0004 — Drizzle as the schema source of truth

**Status**: Accepted — 2026-08-17

## Context

The initial schema (`db/init/001_schema.sql`, `002_rls.sql`, `003_grants.sql`)
was hand-written raw SQL, applied via `docker-entrypoint-initdb.d` on container
init. The stack table in the plan already commits to Drizzle ORM for data
access. Building the `PageRepositoryPort`/`PageVersionRepositoryPort` Postgres
adapter requires deciding how the two coexist: does Drizzle's `schema.ts` become
the source of truth (with `drizzle-kit` migrations replacing the raw SQL), or
does the raw SQL stay authoritative while Drizzle is only used for type-safe
query building, kept in sync by hand?

## Decision

Drizzle becomes the source of truth. `libs/adapters/postgres-db/src/lib/schema.ts`
defines all 7 tables (mirroring the retired raw SQL exactly, including one fix:
`pages.content` now defaults to `'[]'::jsonb`, an empty array, matching the
actual `PageContent = Block[]` domain type — the old raw-SQL default of `'{}'`
was a latent inconsistency that never mattered because the app always writes an
explicit value on create, but was wrong on its own terms).

`db/init/001_schema.sql`, `002_rls.sql` and `003_grants.sql` are removed.
`db/init/000_roles.sh` stays: it creates the `kometio_app` role, which needs a
secret (`POSTGRES_APP_PASSWORD`) that a checked-in migration file can't hold.

Migrations live in `libs/adapters/postgres-db/drizzle/`:

- `0000_initial_schema.sql` — generated by `drizzle-kit generate` from
  `schema.ts` (tables, indexes, FKs, checks).
- `0001_rls_and_grants.sql` — hand-written custom migration (`drizzle-kit
generate --custom`), since Drizzle's schema builder doesn't express RLS
  policies or grants. Ported directly from the retired `002_rls.sql` +
  `003_grants.sql`, unchanged in substance.

A new shared library, `libs/adapters/postgres-db`, holds the schema, the
Drizzle client factory, and a `withTenant()` helper that every Postgres adapter
must use to scope a query to a tenant (`set_config('app.current_tenant_id', …,
true)` inside a transaction — transaction-local, not session-wide, because
connections are pooled and reused across requests for different tenants).
`libs/adapters/postgres-page-repository` depends on it; future Postgres
adapters (auth, media) will too, rather than each redefining the same tables.

Migrations run as the admin/superuser (creating RLS policies and granting
privileges requires table-owner rights — see
[ADR-0002](0002-non-superuser-role-for-rls-enforcement.md)); the app itself
always connects as `kometio_app`.

Verified equivalent to the retired raw SQL: fresh container, migrated schema,
same tables/RLS/grants inspected via `psql`, and the same manual two-tenant
isolation test repeated with identical results.

## Consequences

- One source of truth for the schema — no more hand-syncing SQL and Drizzle
  types.
- `libs/adapters/postgres-db` is a second library not in the plan's original
  "indicative" tree (after `libs/application`, see
  [ADR-0003](0003-separate-application-layer-for-use-cases.md)) — accepted for
  the same reason: Drizzle needs one schema module for its relations/migrations
  to work, and every future Postgres adapter needs the same tenant-scoping
  helper, so duplicating either per-adapter would be the actual violation of
  the plan's own DRY principle.
- Future schema changes go through `pnpm --filter @kometio/postgres-db run
db:generate`, with generated SQL reviewed before committing — RLS/grants
  changes still need a hand-written custom migration, Drizzle won't generate
  those for you.
- Local dev and CI both need `db:migrate` run explicitly after Postgres comes
  up (not automatic yet — automatic migration on app boot is Phase 6 scope per
  the plan, not before).

## Update 2026-08-29 — migration history squashed

By this date the incremental history above had grown to 31 files
(`0000_initial_schema.sql` … `0030_pages_sibling_scoped_slug_uniqueness.sql`).
With no production database yet to protect (pre-launch), the whole chain was
squashed back down to a single `0000_baseline_schema.sql`, generated fresh
from the then-current `schema.ts` and hand-extended with every piece no
migration file could regenerate on its own: the RLS policies + grants
(originally `0001_rls_and_grants.sql`, later extended per-table across
`0003`/`0005`/`0008`/`0012`/`0025`) and the generated `pages.search_vector`
tsvector column (originally `0017_pages_search_vector.sql`). Same session
also converted the 7 `text` + `CHECK` enum-like columns to native `pgEnum`
types (see [[db-schema-cleanup-deferred-2026-08-28]] persistent-memory note
for why that had been deferred, and what changed the calculus). Verified
identically to how this ADR's original decision was verified: fresh
container, migrated schema, RLS/grants/enums/generated-column inspected live
via `psql`, plus a real `pg_dump`/`pg_restore` round-trip. Every other
migration file's _effect_ (as opposed to its literal SQL) is preserved
because the baseline reflects the schema's final, current state — anything
added and later reverted by a subsequent migration (e.g. `sites.theme_tokens`,
added in `0023` and dropped in `0026`) correctly never appears at all.
